# 🏛️ Система учета и обработки обращений граждан

Веб-приложение для автоматизации процесса подачи, распределения и аналитики обращений граждан в государственные ведомства. Проект построен на базе микросервисной архитектуры с разделением на независимый бэкенд (Go), фронтенд (React) и базу данных (MySQL), оркеструемых через Docker Compose.

---

## 🛠️ Технологический стек

### Бэкенд (Backend)

* **Язык разработки:** Go 1.26
* **Веб-фреймворк:** Iris v12 (высокопроизводительный HTTP-движок)
* **Архитектура:** Clean Architecture (domain / usecase / repository / delivery)
* **Работа с БД:** sqlx + go-sql-driver/mysql, миграции — golang-migrate
* **Аутентификация:** JWT (JSON Web Tokens) с разделением ролей (*citizen* / *employee* / *admin*)
* **Безопасность:** хеширование паролей Bcrypt, минимизированные контейнеры

### Фронтенд (Frontend)

* **Библиотека интерфейса:** React 19 + Vite
* **Язык:** TypeScript
* **Работа с сервером:** TanStack React Query
* **UI-компоненты:** PrimeReact (тема lara-light-green)
* **Стилизация:** Tailwind CSS v4 (утилитарные стили с нативной поддержкой состояний элементов)
* **Графики:** Recharts (аналитика по статусам и ведомствам)
* **Маршрутизация:** React Router (SPA)
* **Сервер раздачи статики:** Nginx (с кастомным роутингом под SPA)

### База данных и DevOps

* **СУБД:** MySQL 8.4 (реляционная база данных)
* **Оркестрация:** Docker / Docker Compose
* **Автоматизация:** GNU Make (кроссплатформенный Makefile)

## 🚀 Быстрый запуск

### Требования к окружению

Для запуска проекта на локальной машине необходимы:

1. **Docker Desktop** (включая Docker Compose)
2. **GNU Make** (для Windows 11 устанавливается через `winget install ezwinports.make`)

### Запуск системы одной командой

Склонируйте репозиторий, перейдите в корневую папку и выполните:

```bash
make up
```

Команда автоматически соберет Docker-образы для фронтенда и бэкенда, поднимет контейнер базы данных, дождется его полной готовности (`healthcheck`) и применит все миграции вместе с демонстрационными данными. Приложение будет доступно на `http://localhost`.

## 🕹️ Управление проектом (Команды Make)

В корне проекта настроен `Makefile` для быстрой работы с контейнерами без необходимости ввода длинных консольных команд:

* `make up` — Собрать и запустить все сервисы в фоновом режиме (приложение доступно на порту `80`).
* `make ps` — Проверить статус запущенных контейнеров и проброшенные порты.
* `make logs` — Просмотр логов всех сервисов в реальном времени (выход по `Ctrl + C`).
* `make restart` — Быстрый перезапуск всех модулей системы.
* `make build` — Принудительно пересобрать образы фронтенда и бэкенда без использования кэша.
* `make down` — Остановить работу приложения и погасить контейнеры.
* `make clean` — Полная очистка системы: удаляет контейнеры, внутренние сети и **сбрасывает базу данных** до начального состояния (удаляет volume).

## 👥 Роли пользователей

Система разделяет три роли с разными правами доступа:

* **Гражданин (citizen)** — подает обращения через личный кабинет, видит только свои обращения и их статус/резолюцию. Регистрация выполняется самостоятельно на странице `/register`.
* **Сотрудник (employee)** — работает только с обращениями, назначенными лично ему (`/workspace`); может перевести обращение в статус «В работе» / «Решено» с резолюцией; видит собственную аналитику (графики по статусам и нагрузке).
* **Администратор (admin)** — управляет учетными записями сотрудников (создание с временным паролем, редактирование, мягкая деактивация), ведомствами (создание/удаление), назначает исполнителей на обращения и видит полную аналитику по системе (`/admin/dashboard`).

Ведомство обращения — производное значение: оно всегда наследуется от ведомства назначенного исполнителя (`users.department_id`) и не задается вручную на самом обращении, чтобы исключить рассинхронизацию.

Каждый пользователь может сменить собственный пароль через кнопку «Сменить пароль» в шапке приложения (актуально в первую очередь для сотрудников, получающих временный пароль от администратора при создании учетной записи).

## 📊 Архитектурные особенности проекта

1. **Безопасность (CVE Mitigation):** В рантайм-образах Docker используется автоматический апгрейд пакетов (`apk upgrade`), что снижает количество критических уязвимостей в системных библиотеках до нуля.
2. **SPA Routing на Nginx:** Конфигурация веб-сервера фронтенда перехватывает запросы к несуществующим роутам (`try_files`) и перенаправляет их на `index.html`, исключая появление ошибок `404 Not Found` при обновлении страниц в браузере.
3. **Оптимизация БД:** На уровне СУБД спроектированы B-Tree индексы для составных выборок (по статусам, датам создания и дедлайнам), обеспечивая высокую скорость фильтрации при росте объема данных.
4. **Устойчивый к типам RBAC-слой (Go):** Архитектура авторизационного middleware (`RoleMiddleware`) учитывает особенности строгой типизации Go. Механизм извлечения роли пользователя защищен от ошибок приведения интерфейсов (`interface{}`) и стабильно обрабатывает как примитивные типы (`string`), так и комплексные доменные структуры (`domain.User`), переданные из смежных middleware аутентификации.
5. **Защита от Race Condition при Preflight (CORS):** Слой авторизации бэкенда нативно обрабатывает и пропускает предварительные HTTP-запросы OPTIONS (CORS Preflight) без принудительной валидации JWT. Это гарантирует стабильную работу SPA-клиента (исключает ложные ответы 401 Unauthorized) при мгновенных автоматических запросах данных сразу после успешного логина и перехода на защищенный роут (`/workspace`).
6. **Нативная стилизация состояний без конфликтов типов (TypeScript):** Кастомизация интерфейса PrimeReact инкапсулирована в строковые декларации PassThrough (`pt: { root: { className: ... } }`) с использованием селекторов Tailwind CSS (например, `disabled:`, `hover:`). Это позволяет отказаться от потенциально опасных динамических JS-функций внутри разметки, снижая нагрузку на рендеринг и исключая конфликты несовместимости типов в компиляторе TypeScript.
7. **Статус «Просрочено» как вычисляемое значение:** В базе данных обращение никогда не хранится со статусом `overdue` — он вычисляется на лету (`in_work` + прошедший дедлайн) как на бэкенде (для счетчиков и фильтров), так и в списках фронтенда. Бэкенд дополнительно отклоняет попытку явно проставить `overdue` через API (`400 Bad Request`), поэтому рассинхрон между «фактически просрочено» и «записано в БД» структурно невозможен.
8. **Ролевая изоляция данных (RBAC на уровне выборок):** Список обращений, счетчики (`/stats/realtime`) и историческая аналитика (`/stats/summary`) для роли *employee* принудительно фильтруются по `assignee_id` на уровне usecase-слоя — сотрудник физически не может получить доступ к чужим обращениям или общесистемной статистике даже при прямом обращении к API.
9. **Мягкое удаление пользователей:** Деактивация учетной записи (`DELETE /admin/users/{id}`) не удаляет строку физически, а переводит пользователя в статус «Заблокирован» и блокирует последующий вход. Это сохраняет ссылочную целостность истории обращений и позволяет восстановить доступ администратору.
